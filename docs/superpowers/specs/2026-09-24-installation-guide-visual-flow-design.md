# インストールガイドの視覚化と導線整理

## 背景

現在の導入手順は、README、導入ガイド、OS別Quick Startを順に読む構成になっている。
試用版の検証条件を守るための情報は揃っているが、利用者が最初に実行すべきコマンドと、Studioで確認すべき画面が複数ページに分散している。

インストール方法を一つの入口へ集約し、最初の起動から試用操作までを画像付きで追える構成へ変更する。

## 決定事項

導入ガイドをハブにし、OS別の手順を同じページ内の折りたたみセクションへ配置する。

試用版のインストールとsource checkoutの `python -m pip install .` は同じページで扱うが、同じ手順として混ぜない。

READMEは導入ガイドへ直接誘導し、最初の画面を示す画像と導入経路の選択だけを置く。

OS別Quick Startは、配布ZIPに同梱する詳細なqualification、診断、フィードバック資料として残す。
通常の利用者は、導入ガイドから別ページへ移動せずに起動まで進める。

## スクリーンショット

実際のQt画面を、管理されたサンプルデータと一時ディレクトリを使って再現する。
次の4枚を公開ドキュメントの共通素材とする。

1. `01-welcome.png`：起動直後のWelcome画面。
2. `02-try-sample.png`：Try Sampleでサンプルを読み込んだ画面。
3. `03-asd.png`：Crop後にASDを表示した画面。
4. `04-reopen-project.png`：保存したprojectを再オープンした画面。

画像は `docs/images/installation/` に置き、`scripts/capture_installation_screenshots.py` で再生成できるようにする。
画像生成時に利用者のファイルパス、ホスト名、測定データ、認証情報を含めない。

画像の生成が実機のOS差分に依存しないよう、共通のアプリケーション画面だけを収録する。
WSL2やmacOS固有のQtライブラリ診断画面は、画像ではなく導入ガイド内の短い確認手順で説明する。

## ページ構成

導入ガイドは次の順序で構成する。

1. 「このページだけで起動できます」という短い説明。
2. 試用版とsource checkoutの選択。
3. Ubuntu、WSL2、macOSの折りたたみセクション。
4. 各OSのダウンロード、checksum、preflight、wheel install、起動コマンド。
5. 共通4枚のスクリーンショットを、対応する操作の直前に配置。
6. `pip check`、GUI起動、最初の操作を確認するチェックリスト。
7. 起動できない場合の最小限の診断と、詳細資料へのリンク。

GitHubのMarkdownで利用できる `<details>` を使う。
JavaScript依存のタブ切り替えは導入しない。

## 検証

画像ファイルの存在、PNG形式、Markdownからの相対リンク、公開ソースallowlistへの収録を自動検査する。

スクリーンショット生成スクリプトは、生成先を引数で受け取り、既存の資産を暗黙に変更しない。
生成後に4枚のサイズとファイル名を検査し、導入ガイドとREADMEから参照できることを確認する。

既存のrelease、trial、GUIテストを実行し、アプリケーションの動作変更がないことを確認する。

## 対象外

- Studio本体のUIや操作仕様の変更。
- 試用版のqualification条件の緩和。
- `pip install .` を試用版wheelの代替経路にすること。
- OS固有の実機画面を、未検証の環境から公開画像として作成すること。
- AI生成画像を実画面の代用にすること。
