# GWexpy Studio 0.1.0a1 trial readiness

This document defines the M1 through M4 contract for the first wheel-based
trial.

It does not claim that a wheel, a GitHub prerelease, or a PyPI release already
exists.

The trial is for researchers and students who can create a conda environment
and use `pip`, but should not need Git, a source checkout, or an editable
install.

## M1: public source identity

The private development repository produces a curated canonical snapshot `S`.

The public repository commits that content as `P`.

`M` is a detached canonical source manifest with each relative path, file type,
portable mode, and file SHA-256 in byte-sorted order.

M1 passes only when:

```text
manifest(S) == manifest(P) == M
```

`manifest(P)` ignores only the local top-level `.git` checkout metadata.

It does not ignore excluded, denied, unclassified, symbolic-link, special-file,
or unsafe-permission entries.

Directory modes are normalized to `0755`.

Regular files are normalized to `0755` when executable and `0644` otherwise,
which is the portable executable information Git retains.

The public snapshot contains product source, public tests, fixtures, schemas,
assets, packaging metadata, source-identity tooling, contributor documentation,
and public CI.

The trial-wheel build and publish workflows are included in the M1 public source.

M2 first builds and qualifies the trial wheel with those workflows.

It excludes private audit evidence, internal notes, private workflow data,
private test contracts, harness configuration, and local build products.

The public source verifier reads `P` directly and never re-exports it to prove
the equality.

## M2: installable trial wheel

One pure-Python Studio wheel is built from exactly `P`.

The wheel is tested unchanged on Linux x86_64 and Linux aarch64.

Architecture-specific runtime closures are resolved and recorded separately.

The trial asset contains:

```text
gwexpy_studio-0.1.0a1+trial....whl
constraints-ubuntu24-x86_64.txt
constraints-ubuntu24-aarch64.txt
resolution-ubuntu24-x86_64.json
resolution-ubuntu24-aarch64.json
SOURCE-MANIFEST.json
TRIAL-MANIFEST.json
SHA256SUMS
Quick-Start.*
```

The constraints are runtime-only and architecture-specific.

Each resolution record includes the full Python patch version, pip version,
machine architecture, glibc version, selected wheel filenames and hashes, and
canonical path-free projections of `pip --report` and post-install `pip
inspect`.  The record stores SHA-256 values for those projections rather than
the raw pip JSON, which can contain local paths and repository URLs.

It also records the direct Qt GL host runtime as installed `dpkg` records for
`libegl1` and `libgl1`, with the matching architecture and the required
`libEGL.so.1` and `libGL.so.1` SONAMEs.  The capture fails if either library
cannot load.  Mesa vendor packages, GPU drivers, and display-server records
are outside this M2 evidence boundary.

The installation command uses `--only-binary=:all:` so that a participant does
not unexpectedly start a C or Fortran build.

The GUI dependency is a base wheel dependency before the trial is published.

The M2 technical gate requires wheel installation, launcher startup, Welcome,
Try Sample, Crop, ASD, save/reopen, recovery, and worker cleanup on both
architectures.

Optional I/O backends do not have to match between architectures unless they
are declared part of the trial closure.

## Build and publish boundary

The build workflow has `contents: read` only.

It creates the wheel, source/build manifests, dependency records, checksums,
and technical-gate artifacts.

The publish workflow has `actions: read` and `contents: write` only.

It accepts an explicit build run identifier rather than selecting a latest
artifact.

Before publishing, it verifies the repository, build workflow identity,
successful conclusion, source commit, expected artifact name and digest,
checksums, source manifest, trial manifest, and both architecture gates.

The build ID and trial version are generated by CI from `P`, the UTC date, the
run number, and the attempt number.

For workflow run ID `R` and attempt `A`, the immutable build artifacts are
named with both values.  In particular, the only publishable final asset is:

```text
trial-bundle-R-aA
```

This lets a rerun create a distinct trial version and bundle without replacing
the immutable artifacts from an earlier attempt of the same workflow run.

`TRIAL-MANIFEST.json` records `M`, the allowed generated build-time files, the
staging-manifest digest, the build ID, wheel version, wheel hash, and both
architecture resolution records.

This distinguishes unchanged canonical source from the permitted build-time
delta.

Publish uses a protected `trial-publish` environment and a single concurrency
group with `cancel-in-progress: false`.

It checks that `P` is the default-branch HEAD before environment approval and
again after approval.

If HEAD changed, publishing fails and the wheel must be rebuilt.

The trial tag has the form:

```text
trial-0.1.0a1-p.<short-sha>-r<run>-a<attempt>
```

The workflow verifies both the tag target and the release tag target are `P`.

It creates a prerelease and never reuses or retags a trial tag.

`v0.1.0a1` remains reserved for the later PyPI alpha milestone.

## Required repository setting before a first trial publish

Before dispatching `Publish trial prerelease`, a repository administrator must
create the `trial-publish` GitHub Environment and configure it as follows.

1. Require at least one reviewer.
2. Enable prevention of self-review when the project's release governance
   requires independent approval.
3. Restrict deployment to the default branch.

The workflow requests that named environment, but YAML cannot create its
reviewer or branch-protection policy.  Do not dispatch the publish workflow
until this setting has been verified in the public repository.

## I/O capability boundary

Release policy assigns each direction a static Tier A, B, or C.

The GUI reads that policy before worker startup, but does not import optional
backends itself.

The worker bootstrap performs data-free backend and registry probes and returns
an effective capability snapshot.

```text
Tier A + probe success               -> Verified
Tier B + probe success               -> Experimental
Tier A + missing dependency          -> Unavailable(runtime_dependency_missing)
manifest entry + registry disappeared -> Unavailable(registry_missing)
registry entry + manifest absent     -> Unavailable(unreviewed_registry_entry)
```

Probe failure is fail-closed and exposes only a safe reason.

The same effective capability applies to UI presentation, explicit read,
automatic identification, and write operations.

The snapshot and its digest are included in path-free diagnostics.

## M3: Ubuntu 24.04 human trial

Technical qualification uses the reference Ubuntu 24.04 x86_64 workstation.

The human trial uses three people other than the Studio developer.

Before remediation, the Ubuntu reference-machine qualification records the Qt
GL preflight result for `libEGL.so.1` and `libGL.so.1`.  If either library is
missing, it records the failed baseline, installs `libegl1` and `libgl1`, and
records the successful preflight and package versions after remediation.

The installation and launch gate is three of three without intervention.

At least two of three participants must complete the five-minute workflow.

The five-minute timer starts after the Welcome screen is visible.

No P0 issue and no project/recovery P1 issue may remain.

The same P1 issue for two or more people stops the trial for a fix.

## M4: Windows 11 with WSL2 and WSLg

Both physical technical configurations are required:

```text
Windows 11 x86_64 + WSL2 Ubuntu 24.04 x86_64 + WSLg
Windows 11 ARM64  + WSL2 Ubuntu 24.04 aarch64 + WSLg
```

Each verifies conda setup, wheel install, WSLg display and scaling, clipboard,
worker spawn/exit, shared-memory cleanup, Linux and `/mnt/c` paths, Japanese
and spaced paths, project save/reopen, source change detection, recovery, and
Python export.

For each WSLg configuration, the Ubuntu distribution records the same Qt GL
preflight before remediation.  A missing `libEGL.so.1` or `libGL.so.1` is
repaired inside that Ubuntu distribution with `libegl1` and `libgl1`, then the
post-remediation preflight and package versions are recorded before GUI
qualification continues.

The human trial again has three people total, including at least one x86_64 WSL2
participant and at least one ARM64 WSL2 participant.

An ARM Chromebook is an additional Linux aarch64 smoke test only.

Its operating-system and glibc baseline are recorded so an incompatible
container is not treated as a Studio architecture failure.

## Out of scope until after M4

M1 through M4 do not publish to PyPI, create an AppImage, create a native
Windows installer, or create a macOS app.

Those distribution paths are reconsidered after human-trial feedback.
