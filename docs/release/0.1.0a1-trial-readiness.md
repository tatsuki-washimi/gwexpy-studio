# GWexpy Studio 0.1.0a1 trial readiness

This document is for release owners and reviewers.
It defines the source, build, qualification, publication, and human-trial boundaries for the four-target trial.

## Source identity before `P_trial`

Before fixing `P_trial`, the private snapshot `S`, public commit `P`, and detached canonical manifest `M` must satisfy:

```text
manifest(S) == manifest(P) == M
```

The public-source verifier scans `P` directly and ignores only top-level `.git` checkout metadata.
Product code, tests, schemas, assets, packaging metadata, documentation, public CI, and trial workflows are included in the M1 public source.
Private evidence, internal notes, harness configuration, and local build products remain excluded.

After these conditions hold, `P_trial` is one fixed public source commit.
All four targets must be built from `P_trial`, and the default branch must remain unchanged from the first formal Build through publication verification.
The M2 path first builds and qualifies the wheel through the public workflows; the current four-target candidate remains a separate, unfinished execution.

| Target | Physical configurations | Publication group |
| --- | --- | --- |
| `ubuntu24-x86_64` | native Ubuntu 24.04, x86_64 | Ubuntu |
| `debian13-x86_64` | native Debian 13, x86_64 | Debian |

The trial requires four targets and five physical configurations.
Native Linux, WSL2, and macOS are distinct environments.
Unknown targets and mismatched OS or CPU values are rejected.

## Source, build, and assets

Each target Release contains exactly two participant assets: a target-qualified ZIP and its matching outer SHA-256 sidecar.
The ZIP contains the wheel, matching constraints, internal checksums, Build identity, target Quick Start, and Japanese feedback form.
The feedback file is named `Feedback.ja.md`.
The Quick Start bytes are frozen from the source manifest; Build and Publish do not replace them.

Build and Publish remain separate.
Build produces target artifacts, metadata, and a qualification kit without publishing a Release.
The Publish workflow verifies the selected Build/run/artifact identity and checks only that the supplied qualification-summary input has the required SHA-256 form; it does not fetch or validate the summary or its evidence.
The parent and F run the pre-publication verifier against the actual distribution ZIPs and trusted Build metadata, then pass its concrete result and the approved hash summary into the human approval record.
An explicit human approval is required immediately before manual workflow dispatch.

The resolution record is schema 4 and includes the target, conda kind and version, subdir, requested Python and pip, and aligned package name, version, and build records for each installation phase.
Formal verification uses dedicated conda Python 3.12 environments and does not fall back to venv.
The Ubuntu reference preflight records `libEGL.so.1` and `libGL.so.1` before remediation; if required, the documented runtime packages are installed and the post-remediation state is recorded.

Qualification evidence is schema 2.
It binds source SHA, target, CPU, Build ID, wheel hash, ZIP hash, and kit manifest hash.
Automatic checks and owner checks are separate fields.
Missing, unanswered, EOF, interrupted, failed cleanup, or unsaved results are not passing evidence.
Canonical evidence contains no path, username, hostname, owner contact information, or freeform logs.
Display-scale settings are recorded as a boolean pass or fail in canonical evidence; numeric scale values remain in private owner work notes.

## Physical owner qualification

The selected Build workflow’s original kit artifact is the formal handoff artifact and must be preserved for later trusted summary verification. The following Build/operator interface describes how the release owner creates a source-bound kit from the selected Build; a locally created kit does not replace the original Build artifact. The release owner hands the matching kit to the owner for one physical configuration. The owner does not need Git, a source checkout, or any source operation.

The release-owner build command is:

```bash
python3 scripts/build_qualification_kit.py \
  --release /path/to/target-release \
  --output /path/to/qualification-kit-ubuntu24-x86_64-BUILD_ID \
  --trial-target ubuntu24-x86_64
```

The owner starts the supplied `run-qualification.sh` from a Bash-capable native terminal, using a fresh working copy of the untouched kit. Change the current directory to that fresh copy containing `run-qualification.sh` before running the command. This invocation also works when artifact extraction has removed the launcher’s executable bit:

```bash
set -eu
conda_base="$(conda info --base)"
test -x "$conda_base/bin/conda"
CONDA_EXE="$conda_base/bin/conda" bash ./run-qualification.sh
```

On WSL2, run this in the matching Ubuntu guest and select that guest’s conda executable. On macOS, run it in the macOS terminal with the native conda executable. The launcher uses `CONDA_EXE`, invokes `conda run -n base`, creates temporary Python 3.12 environments, and writes the result below the working copy’s `results/` directory. It does not forward extra launcher arguments. The owner receives a prebuilt kit and does not run Git or source commands.

The accepted verifier descriptor and command procedure are in [Qualification.md](../trial/Qualification.md).

The order is fixed:

```text
preconditions and checksums
→ install into a temporary conda environment
→ automatic qualification
→ owner checks in the same environment
→ cleanup
→ save the final result
```

The owner checks the native file dialog with a Japanese path containing spaces, then checks the normal display scale and one other available scale.
All five configurations are required; an unassigned or unavailable owner is not a pass.
The owner answers the five bounded prompts with `y`, `n`, or `c`: native dialog path selection, normal-scale display, normal-scale operation, available alternate-scale display, and available alternate-scale operation. Canonical evidence stores only the resulting booleans; numeric scale values remain in a private owner memo.

EOF, an unanswered prompt, `n`, `c`, interruption, cleanup failure, result-save failure, or any missing final result is nonpass. The runner does not overwrite an existing result or reuse an existing work root. Preserve failed evidence and the untouched original Build artifact, then use a fresh working copy for a rerun. Owner results remain separate from the original Build artifact so the later trusted summary can verify the exact Build and kit hashes.

## Publication groups and publication boundary

| Group | Required passing evidence |
| --- | --- |
| Ubuntu | native Ubuntu configuration |
| Debian | native Debian configuration |
| WSL2 + Mac | both WSL2 configurations and the macOS configuration |

The three group summaries are separate from the five-configuration audit summary.
Each group summary records one source SHA, each Build ID, wheel, ZIP, and kit hash, Build run and artifact identity, and each qualification-result hash.
The pre-publication verifier obtains expected values from the actual verified ZIP and trusted Build metadata. The release operator’s descriptor fields, accepted commands, group mappings, and all-five audit procedure are defined in [Qualification.md](../trial/Qualification.md); its local paths remain private descriptor input.
It rejects missing, duplicate, extra, mixed-candidate, or mismatched evidence.
The Publish inputs remain the explicit Build run ID and the SHA-256 of the complete qualification summary.

The `trial-publish` environment has no required reviewers and uses a default-branch deployment policy.
Explicit human authorization is required before manual workflow dispatch.

The WSL2 and Mac targets share one verified summary.
After that summary is approved, run the existing Publish workflow twice, serially, once for each target.
Do not publish either side from a partial summary.

Tags directly reference `P_trial`.
Each Release is `draft=false`, `prerelease=true`, `latest=false`, and contains only its corresponding ZIP and sidecar.
Existing tags, Releases, and assets are never overwritten.

Before publication dispatch, record the concrete Build run, hash summary, and verified two-asset sets.
After publication, verify the REST and GraphQL state, exact two-asset membership, redownloaded asset bytes, and the verifier result.

An expired artifact is not bypassed.
Build again and repeat the corresponding qualification and group summary.
Even with the same source, a new Build ID requires new qualification evidence and a new group summary.
If one side of the WSL2 + Mac publication is available and the other is not, keep the valid existing Release and resume only the unpublished side.
Never overwrite an incomplete tag or asset.

A source change requires all four targets to be rebuilt and all five physical configurations to be requalified.

## Human trial

Human trial starts after distribution.
It includes at least two WSL2 participants, at least one Mac participant, and at least three participants in total.
All participants must install unassisted, launch unassisted, and complete Save → Close → Open.
At least `ceil(2N / 3)` participants must complete the workflow within five minutes.
P0 and project or recovery P1 counts are zero.
The same P1 root cause affecting two or more participants is a stop condition.
An absent Review or Restore display is not a failure.
An owner who used the qualification kit is not counted as a first-time participant.

On any stop condition, stop recruitment and return the affected Release to draft.
The next run uses a new first-time-user cohort, a new source commit, a new tag and Build ID, and rebuilt qualification evidence and group summary.
Workarounds are recorded as `No` unless the trial contract is explicitly changed.
The Ubuntu and Debian additional participant threshold remains undecided until explicitly approved.

The normal Quick Start does not measure first-time status or trial timing.
The common human-trial record collects those facts after distribution and is checked against the existing human-trial evaluator’s input and gate fields.

## Participant boundaries and known constraints

Participants use the target Quick Start, conda Python 3.12, the supplied wheel, and the supplied constraints.
They do not need Git, a source checkout, an editable install, or PyPI.
They must not change constraints, rebuild from source, substitute a wheel, or use a bundle on another target.

The supported I/O check is the existing TimeSeries CSV read policy.
Other formats or directions may be shown as unavailable and are not expanded by this trial.

The invitation keeps placeholders for the actual Release URL, tested OS version, and response deadline.
Those values are filled from the external distribution list after publication approval; bundled Quick Start bytes remain unchanged.

PyPI, AppImage, DMG, signing, notarization, native Windows installers, and analysis or file-format redesign are outside this trial.
